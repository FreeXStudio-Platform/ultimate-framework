# Documentation, Blueprint, Machine, Visual, and Publication Guide
Every material module uses one stable semantic scope with coordinated representations. Write section by section: discover evidence; define scope/claims; update narrative; update blueprint/visual and machine contracts where applicable; add tests/evidence; update registries/graph; run parity; then move on. Do not manufacture empty JSON or decorative diagrams; record a justified N/A. Generated HTML, PDF, SVG, PNG, Notion pages, and Figma frames remain derivatives or design context, not executable proof. Public and enterprise views derive from approved internal claims through classification, sanitization, rights, unsupported-claim, leak, and freshness checks.

`absolute doc new` / `doc step` / `doc seal` execute exactly this order — `D1.SCOPE` through
`D11.CHANGELOG` — generating each representation from one declared scope so they stay in
parity rather than merely adjacent. `doc seal` refuses on a single unresolved `<<TODO: …>>`
marker, on any missing step, and on any conformance finding against the framework's own
manifest, policy, and visual schemas. A structural heading indented four spaces renders as a
code block and is a hard finding, not a style note: a narrative that publishes as an
undifferentiated blob has lost representation parity while still looking authored.

Without Graphviz the visual step writes a self-describing placeholder SVG carrying the declared
alt text, and deep verification records `VISUAL_PARITY_NOT_RUN` as a finding rather than
skipping it.
