# Absolute Repository, Versioning and Release Operations

## Why this document exists

Two things were true through 1.2.0 and neither was written down: the release payload could not pass
its own tree-integrity control on a working tree, and the procedure for regenerating its
documentation described a directory layout that no longer existed. Both are repository-shaped
problems that no existing document owned.

This document owns the repository and the release *operation*. Runtime order stays in
[SYS-120](SYS-120-runtime-enforcement.md); verification practice stays in
[GUIDE-140](GUIDE-140-operations-verification.md); the normative procedure stays in
`01_control_plane/manifests_releases/RELEASE_PROCEDURE.md`, and this document summarizes it and
points at it rather than replacing it. Two normative copies of one procedure is exactly the drift
this framework exists to prevent.

## Repository layout

### What each root entry is

| root entry | role |
|---|---|
| `absolute-canonical-framework-v1.3.1/` | The release payload — the subject of every integrity control. Its basename must equal `ROOT_NAME`. |
| `engine/` | The vendored documentation and blueprint instrument. Not part of release identity. |
| `_release/` (not committed) | Where the procedure writes the sealed zip and its detached SHA-256. The sealed artifacts are published as GitHub Release assets, never committed. |
| `README.md`, `RELEASE_STAMP.json`, `MANIFEST.sha256`, `.gitignore`, `docs/doc-pipeline/` | The repository's own records. |

The payload is a subdirectory rather than the repository root because `.git` is denylisted inside
the payload by `FORBIDDEN_PARTS`, and the release root's basename is checked against `ROOT_NAME` —
a repository root can be named anything; a release root cannot.

The visual for this layout is [SYS-110](SYS-110-architecture.md)'s `repository-layout` figure;
this document links to it rather than duplicating it.

### What is source and what is regenerated

At operational granularity — the exact command that regenerates each derived set, not only the
architectural claim that it is derived:

- **Source, hand-edited:** module packages, registries, schemas, fixtures, `runtime/`, `tools/`,
  the root documents, `system.spec.json`, `PROJECT_INDEX.json`, the `.dot` graph sources, and the
  authored bodies of the eight documents under `docs/ultimate-engine/`.
- **Regenerated by `scripts/derive_documentation_model.py`:** every `docs/ultimate-engine/machine/*.json`
  the script writes, the `docs/ultimate-engine/*_spec.json` figure sidecars, and the standalone
  `graphs/source/*.mmd` sources.
- **Regenerated by `tools.docgen.cli build`/`index`/`content-index`:** the eight documents' `.html`
  and `.json` builds, `DOCS_INDEX.html`, and `docs/design/doc-system/CONTENT_INDEX.json`.
- **Regenerated by `tools.blueprint build`/`layout`:** `blueprint/*`.
- **Regenerated by the mermaid and graphify tooling:** `graphs/rendered/*.svg` and
  `graphs/structure/*`.
- **Written only by `tools/prepare_release_metadata.py`:** `MANIFEST.json`,
  `CANDIDATE_SOURCE_MANIFEST.json`, `SHA256SUMS.txt`, `.absolute/release/release_identity.json`,
  `.absolute/release/authority_record.json`, and `.absolute/release/gate_binding.json` with its
  `gate_evidence/` records — six files, exactly.
- **Written only by the release/allowlist tooling:** `RELEASE_ALLOWLIST.json`, by
  `01_control_plane/manifests_releases/tools/generate_release_allowlist.py`.

### What never enters git

| class | examples | why it matters to identity |
|---|---|---|
| Harness / session artifacts | `.claude/`, `.codemap/`, `.remember/`, `.DS_Store` | Agent-tooling state, not framework content. |
| Bytecode | `__pycache__/`, `*.pyc` | A tool that writes bytecode into the tree mutates a release that is supposed to be read-only source. |
| Engine-derived host state | `.docgen/`, `.health/`, `.blueprint/`, `graphify-out/`, `node_modules/`, `.docgen_cache.json` | Byproducts of running the instrument against this host, not release content. |
| Release-procedure scratch | `/predecessor/`, `/_staging/`, `/_cleanroom/`, `/_build/` | Working copies used to build or verify a release, never the release itself. |

**The rule that makes this more than housekeeping:** `ALLOWLIST_RECORD_SET_DRIFT` enumerates every
file under the payload root — `__pycache__` is the only exclusion — so an *ignored* file left inside
the payload is still a *file*, and a CRITICAL finding the moment it exists. Set
`PYTHONDONTWRITEBYTECODE=1` for every Python invocation touching the payload; opt out of, or
delete, any host-local run log; check `git status --short --ignored=matching <payload>` before
finishing any session that touched it.

`_release/` and `predecessor/` are both uncommitted working directories. The sealed zip a release
produces under `_release/` is published as a GitHub Release asset with its detached SHA-256; a tree
extracted under `predecessor/` is a local, reproducible act from a hash-verified input, not a second
copy of history to track.

## The version-bump checklist

### The pins

One release version, pinned in nine classes of tracked file. Each class is checked against the
counts in [`machine/release-model.json`](machine/release-model.json)'s `pins`, not typed here:

| pin class | what it is | checked by |
|---|---|---|
| `version_file` | `VERSION` — the single source. | — |
| `release_tooling` | `RELEASE_VERSION`/`RELEASE_ID`/`CANDIDATE_ID`/`ROOT_NAME` and `BASELINE_CHAIN` in `release_integrity.py`. | `FRAMEWORK_IDENTITY` |
| `registries` | `docs/registries/FRAMEWORK.json` `version`/`release_id`/`baseline_chain`/`predecessor_release`. | `FRAMEWORK_REGISTRY_RELEASE_DRIFT` |
| `module_manifests` | 33 × `MODULE_MANIFEST.yaml` `framework_release`. | `MODULE_RELEASE_PIN_DRIFT` |
| `module_narratives` | 33 × `MODULE.md` front-matter `framework_release`. | `MODULE_NARRATIVE_RELEASE_DRIFT` |
| `schemas` | `module_manifest.schema.json` `const`; `release_manifest.schema.json` and `release_allowlist.schema.json` `$id`/`schema_version`. | schema validation |
| `test_manifest` | `09_tests_evals/TEST_MANIFEST.json` `suite_id`. | not mechanically checked — see [REF-150](REF-150-evidence-limitations.md) |
| `governance` | `governance/SUPERSESSION_LEDGER.json`; `governance/coverage_closure_v3/release_surface_registry.json`. | `FRAMEWORK_GOVERNANCE` |
| `allowlist` | `RELEASE_ALLOWLIST.json` `release_id`/`candidate_id`. | `ALLOWLIST_RELEASE_DRIFT` |

### The mass-rewrite surface

A version bump touches 33 narratives, 33 manifests, and — whenever a `.dot` source changes — up to
35 SVGs, all derived counts rather than a hand-kept list. The single command that re-renders every
derivative under the recorded Graphviz build is the same one [GUIDE-140](GUIDE-140-operations-verification.md)
names for ordinary visual regeneration; this document does not enumerate the 33 module names — the
registry is the enumeration.

### The order that avoids a red tree

`VERSION` moves first; then the pins; then the derivatives; then the documentation; then the
allowlist; **then** the release metadata; then the build. Each ordering constraint exists for a
reason, not only by convention:

- the allowlist must follow every file addition or removal, because it declares an **exact** record
  set — regenerating it before the tree stops changing would immediately go stale;
- the release metadata must follow the allowlist, because the candidate hash the metadata binds
  covers the allowlist file itself;
- the metadata runs **twice**, because the gate evidence it writes is derived from a verification
  that ran *before* the metadata was rewritten — only the second run's evidence describes the tree
  the metadata now claims;
- `FRAMEWORK_IDENTITY` and `SIMULATION` are red in the window between freezing the payload and the
  second metadata run, by construction — [SYS-120](SYS-120-runtime-enforcement.md) states exactly
  why.

## The release procedure, in order

Ten steps, mirroring `01_control_plane/manifests_releases/RELEASE_PROCEDURE.md`'s own numbered
headings (`0`–`9`) so this summary cannot drift from the normative procedure it points at.

### 0. Environment

Install the pinned validation dependencies from `04_enforcement/requirements-validation.txt` and a
working Graphviz. If the tree was copied by something that does not preserve UNIX permissions,
repair the executable surface with `tools/restore_modes.py --check` then `tools/restore_modes.py`
before anything else — file modes are not part of the candidate identity, so repairing them cannot
change the release hash.

### 1. Freeze the payload

No edits after the candidate identity is computed, without invalidating all affected and transitive
evidence. The package root's basename must equal `ROOT_NAME`; the tooling refuses any other name.

### 2. Regenerate the release allowlist

From inside the payload:

```sh
python3 01_control_plane/manifests_releases/tools/generate_release_allowlist.py . ../predecessor/absolute-canonical-framework-v1.0.0-rc.2
python3 01_control_plane/manifests_releases/tools/generate_release_allowlist.py . ../predecessor/absolute-canonical-framework-v1.0.0-rc.2 --check
```

The second command exits 0 on `{"status": "PASS"}` and 2 on drift. The output path is forced to the
candidate-local `RELEASE_ALLOWLIST.json`; the baseline root must be the extracted, checksum-verified
RC2 tree — see "The predecessor chain" below for where it comes from in this repository. This step
runs **before** the metadata bind, because the candidate hash the metadata binds covers the
allowlist file itself — see "The order that avoids a red tree" above.

### 3. Bind the release metadata

`python3 tools/prepare_release_metadata.py`, run twice from a dirty state, then confirmed identical
across two further runs. This is the only supported way to write the six hash-binding files. `C20`
is written here as `EXTERNAL_HANDOFF_REQUIRED` and stays that way.

### 4. Verify — all of it, in a fresh process

```sh
python3 tools/deep_verify.py
python3 tools/verifier_mutation_check.py
python3 09_tests_evals/run_all.py
python3 tools/check_no_loss.py --predecessor <extracted predecessor tree>
```

Anything genuinely removed relative to the predecessor must be declared in
`governance/SUPERSESSION_LEDGER.json` with a reason, or `check_no_loss.py` fails.

### 5. Build

```sh
python3 01_control_plane/manifests_releases/tools/build_release.py . OUTPUT.zip \
  --expected-candidate-sha256 <64-hex> \
  --authority-record .absolute/release/authority_record.json \
  --gate-binding .absolute/release/gate_binding.json
```

Dry run first; add `--commit` only once the dry run passes. Recover the expected hash with
`release_integrity.py candidate-hash .`.

### 6. Verify the artifact, not the working tree

Verify the sealed zip itself with `verify_release.py` and `verify_successor_release.py`, then
extract it to a clean directory **preserving file modes** and run `tools/deep_verify.py` there.
`unzip` and `zipfile.extractall()` both drop the executable bit; extract applying the archive's own
recorded mode, or run `tools/restore_modes.py` afterward. The shipped artifact must verify, not
merely the tree it was built from.

### 7. Reproduce

Rebuild from a fresh staging copy and require an identical ZIP SHA-256. Build evidence is a separate
archive, never nested inside the clean package.

### 8. Record

Record detached hashes, sizes, tool versions, raw reports, limitations, the rollback reference, and
the exact independent-certification status.

### 9. Do not rename it

Never relabel a candidate `FINAL` or `CERTIFIED`. The strongest internal state is
`READY_FOR_INDEPENDENT_CERTIFICATION_HANDOFF`, reached only after `C20` delivery succeeds. The party
that builds an artifact may not declare it certified.

## The predecessor chain, and where sealed predecessors live

The chain is RC1 (the immutable input baseline) → RC2 → 1.0.0 → 1.1.0 → 1.2.0 → 1.3.0 (immutable
predecessor releases), with 1.3.0 the immediate predecessor of this release. Each entry carries a
`clean_zip_sha256`, a `build_evidence_zip_sha256`, and from RC2 onward a `candidate_tree_sha256`.

Two roles in this chain are not the same, and confusing them is exactly what broke the allowlist
generator between RC3 and 1.2.0: **RC1 is the input baseline**; **RC2 is the baseline the allowlist
derives source identity from**. The generator looks the RC2 baseline up by release id rather than by
position in the chain, so a later merge changing what sits at `BASELINE_CHAIN[0]` cannot silently
repoint it again.

The public repository does **not** carry the predecessor archives. Their `clean_zip_sha256`,
`build_evidence_zip_sha256` and `candidate_tree_sha256` values are recorded in `BASELINE_CHAIN`, and
verification of a release needs only those recorded values — a clone verifies without any archive.
*Cutting* a release is a maintainer operation: step 2 above needs the extracted, checksum-verified
RC2 tree, which a maintainer supplies from the archive they hold, extracted into the gitignored
`predecessor/` directory. A contribution that adds, removes or edits a payload file therefore
reaches maintainers with the allowlist stale by construction; a maintainer regenerates it, re-binds
the metadata and re-seals. Pull requests do not need to attempt that themselves.

References to `RC1`, `RC2`, or `1.0.0` elsewhere in this tree are historical provenance and do not
identify this release.

## The engine pin

`engine/` is Ultimate Engine **1.0.7**, vendored with `git subtree --squash` (the exact upstream
commit is recorded in `engine/PROVENANCE.md`). It is the documentation and blueprint **instrument**, and is
deliberately **not part of the framework's release identity** — it sits outside the payload and
outside `MANIFEST.json`.

It is vendored rather than referenced so the documentation set can regenerate from a clone without a
sibling checkout. To update it: a `git subtree pull` into `engine/`, recorded as its own commit,
followed by a full regeneration and re-verification of this documentation set — an engine bump can
change generated bytes, so it is a documentation-set change, not a silent dependency update.

Node dependencies for the engine's sub-tools (`engine/`, `engine/tools/visual-engine/`,
`engine/tools/mermaid-engine/`) are installed per sub-engine and `node_modules/` is gitignored:
pinned and reinstallable, not vendored.

Do not edit engine source from a framework session. A calibration, if one is ever required, is
recorded where it happens, not folded silently into a documentation pass.

## Regenerating the documentation set for this layout

```sh
export PYTHONDONTWRITEBYTECODE=1
export ENGINE_HOST_ROOT="$PWD/absolute-canonical-framework-v1.3.1"
export ENGINE_AUTHORED_DOCS_ROOT="docs/ultimate-engine"
export PYTHONPATH="$PWD/engine"

python3 absolute-canonical-framework-v1.3.1/docs/ultimate-engine/scripts/derive_documentation_model.py

python3 -m tools.docgen.cli --strict build \
  absolute-canonical-framework-v1.3.1/docs/ultimate-engine/GUIDE-100-project-guide.md \
  absolute-canonical-framework-v1.3.1/docs/ultimate-engine/SYS-110-architecture.md \
  absolute-canonical-framework-v1.3.1/docs/ultimate-engine/SYS-120-runtime-enforcement.md \
  absolute-canonical-framework-v1.3.1/docs/ultimate-engine/REF-130-extension-points.md \
  absolute-canonical-framework-v1.3.1/docs/ultimate-engine/GUIDE-140-operations-verification.md \
  absolute-canonical-framework-v1.3.1/docs/ultimate-engine/REF-150-evidence-limitations.md \
  absolute-canonical-framework-v1.3.1/docs/ultimate-engine/REF-160-agent-blueprint-guide.md \
  absolute-canonical-framework-v1.3.1/docs/ultimate-engine/GUIDE-170-repository-release.md \
  --formats html,json

(
  cd absolute-canonical-framework-v1.3.1
  python3 -m tools.docgen.cli index docs/ultimate-engine -o docs/ultimate-engine/DOCS_INDEX.html
  python3 -m tools.docgen.cli content-index --docs-root docs/ultimate-engine \
    -o docs/design/doc-system/CONTENT_INDEX.json
)

python3 -m tools.blueprint build
python3 -m tools.blueprint layout
python3 -m tools.blueprint verify

ENGINE_HOST_ROOT="$ENGINE_HOST_ROOT" node engine/tools/graphify/build.mjs
# then copy graph.json / graph-data.js / graph-view.html / vendor/*.js into
# absolute-canonical-framework-v1.3.1/docs/ultimate-engine/graphs/structure/, as this file's own
# regeneration run does — never build.log, which embeds wall-clock time and is not deterministic

for source in absolute-canonical-framework-v1.3.1/docs/ultimate-engine/graphs/source/*.mmd; do
  name="$(basename "$source" .mmd)"
  node engine/tools/mermaid-engine/render.mjs "$source" \
    -o "absolute-canonical-framework-v1.3.1/docs/ultimate-engine/graphs/rendered/$name.svg"
done

python3 -m tools.project_index.cli dashboard
python3 -m tools.project_index.cli verify --scan docs/ultimate-engine
```

`ENGINE_AUTHORED_DOCS_ROOT` is a real, config-declared setting
(`engine.config.json`'s `docSystem.authoredDocsRoot`), read dynamically rather than hardcoded —
worth stating so a reader does not go looking for this layout in the Python source itself.

Two honest notes, re-verified for this layout rather than assumed: the optional SQLite blueprint
index (`tools.blueprint index`) refuses with an empty `gatekeepers` table on this host, because the
engine imported its own gate registry while this subject exposes no host-owned blueprint gatekeeper
relationships — that refusal is correct, and no SQLite file is committed to work around it. The
structure graph's `build.log` is deliberately not copied because it embeds wall-clock time; the
graph JSON itself carries a deterministic `content_version` instead.

`blueprint layout` may decline to write an SVG when straight-line edge routing would cross a
non-endpoint node. That is a named renderer limit, not permission to hand-draw the missing figure.

`PROJECT_INDEX.json` is an intentionally maintained registry, not a filesystem scan.
`tools.project_index.cli register` adds or changes one row, `dashboard` rebuilds the HTML, and
`verify --scan docs/ultimate-engine` checks the registry against the tree.

## GitHub conventions

This repository is published as a **public** repository, default branch `main`, with one annotated
tag per release in the form `vX.Y.Z`. Release assets are **the sealed zip and its detached
`.sha256`**, never a tarball of the working tree.

What never enters git is stated in full above, under "What never enters git," plus the extracted
predecessor trees under `predecessor/`.

The tag is not the release. A tag names a **commit**; the release identity names a **candidate tree
hash**. They are different objects, and the sealed zip — verified against the candidate hash, not
against a commit — is the one that carries the framework's actual identity guarantee.
[GUIDE-100](GUIDE-100-project-guide.md)'s "two identity systems" section states the general version
of this distinction; this is its repository-specific instance.

## What "first stable release" means here

It means: internally verified, deterministic, reproducible from a recorded environment, with a
complete predecessor chain and no undeclared removals — and **independent certification pending**.

It does **not** mean certified, audited, or externally reviewed. Gate `C20` is
`EXTERNAL_HANDOFF_REQUIRED`; the party that builds an artifact may not declare it certified. The one
sentence to use when writing about this release, quoted exactly: *"internally verified, independent
certification pending."*
